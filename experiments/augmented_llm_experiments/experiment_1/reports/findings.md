# Qualitative findings

## Scope

These experiments tested the model directly, not the full `AugmentedLLM` loop. For the answer stage, the `read_file` result was fabricated by the experiment harness as a fixed fixture, not generated by the model or read from disk. One greedy-decoding response was collected for each case. The Llama 3B model used 4-bit NF4; Llama 1B and LFM used float16. The comparison is exploratory and not precision-controlled.

## Tool-selection results

The current branch instruction was the only initial instruction that produced correctly marked calls for any of the three file-request cases. Llama 1B produced 2/3 calls and Llama 3B produced 1/3; LFM produced 0/3. The three other initial instructions produced 0/3 for all three models. Those are very small samples.

A valid call does not mean a safe or coherent full response. In Llama 1B's branch `read_notes` case, the model emitted the correct call and then asked for the already-provided path. In Llama 3B's branch `read_code` case it emitted a correct call but also described the file before receiving any actual result. Both count as passes under the format/path check. See [Llama 1B branch](../results/llama1b/branch.md) and [Llama 3B branch](../results/llama3b/branch.md).

LFM frequently produced learned formats such as `<|tool_call_start|>...<|tool_call_end|>` or asked for the file contents instead of using this repository's custom markers. Those outputs were not counted as valid calls. See [LFM grounded](../results/lfm1b/grounded.md) and [LFM minimal example](../results/lfm1b/minimal_examples.md). This experiment did not enable Hugging Face native tool calling.

The no-tool score only verifies that a call was not detected. For example, the compact prompt passed Llama 1B's arithmetic routing check even though the response asked for a file containing the numbers. It also passed Llama 3B's arithmetic routing check when the model asked for a calculator. Review answer content, not only the score.

## Answering after a simulated result

The strongest initial candidate for natural, grounded answers in this small suite was the **grounded** instruction with a labeled JSON result and Llama 3B: it matched the automatic checks for all four fixtures and mentioned no tools. Its direct factual answer was “The maximum temperature is 37 C.” Its summary retained the greenhouse, Raspberry Pi, sensors, and testing details. See [Llama 3B grounded](../results/llama3b/grounded.md).

Even that candidate needs careful review. On the truncated fixture, Llama 3B said the *file* appeared truncated, while the fixture says only the returned content was truncated. That nuance matters. Its same grounded instruction produced no valid marked calls for the three tool-needed selection cases, so it is not a reliable complete agent prompt based on this evidence.

LFM gave natural grounded answers for the summary, numerical fact, and missing-file examples; it omitted the partial-content warning in the initial grounded case. The branch missing-file response was sensible but failed the automatic keyword check because it did not repeat the filename. See [LFM grounded](../results/lfm1b/grounded.md) and [LFM branch](../results/lfm1b/branch.md).

A false positive illustrates why the answer scores are not semantic grades: Llama 1B's branch summary included all expected keywords but invented a claim that the file was 10 characters long. It passed the keyword check. See [Llama 1B branch](../results/llama1b/branch.md).

## Practical next step

Use the grounded instruction and labeled observation as a **candidate for the post-tool answer stage**, not as a proven solution. It asks the model to answer naturally from the actual result and avoid describing the tool mechanism. The exact instruction and messages are recorded in the linked results and `data/design.json`. Keep tool selection separate in evaluation, preserve the original user request, and test missing, partial, and misleading inputs before changing the agent.

The initial `grounded` and `compact` variants differ in both instruction and observation formatting. Their scores do not show which change caused an outcome. The follow-up holds the grounded instruction fixed and compares three observation presentations; see the automatic summary and the corresponding `grounded`, `grounded_raw_json`, and `grounded_plain` result files.

## Controlled observation-format follow-up

The same grounded system instruction was used with three presentations of the same four fixtures: the initial labeled JSON, raw JSON, and a plain-language result. Each combination was tried once per model. All three passed the four automatic answer checks for Llama 3B, while both 1B models omitted the partial-content warning for all three presentations.

The wording still differed: for the partial fixture Llama 3B with raw JSON said “The content is truncated,” and with the plain-language result said “The content of notes.txt is partial.” Both are more precise than its labeled-JSON response saying the file appeared truncated. In contrast, Llama 1B's plain-language summary invented claims about progress and performance even though the fixture only described the project and its testing status. See [3B raw JSON](../results/llama3b/grounded_raw_json.md), [3B plain result](../results/llama3b/grounded_plain.md), and [1B plain result](../results/llama1b/grounded_plain.md).

For a first implementation experiment, the grounded instruction plus raw JSON is therefore a reasonable **answer-stage candidate** on the tested 3B model. Do not infer that raw JSON is generally superior: four fixtures and one generation each are not sufficient to establish that, and tool selection still failed under the same instruction.

The LFM model used a reference PyTorch implementation because the optional `causal_conv1d` kernel was not installed. Durations are recorded for inspection but should not be treated as a fair speed benchmark.

## Human observations

### Answer stage

- Most answer-stage experiments pass my review. When the model receives the user's question together with a simulated tool-call result, it can generally answer the question.
- Some answers, particularly from Llama 3.2 1B, include unnatural JSON or other information the user did not ask for.

### Tool selection

- Most selection-stage experiments fail my review. Some responses do not contain a tool call, while others use incorrect tool markers.
- Some responses contain a correctly marked tool call but also include text that may be unnecessary or confusing, such as “I'll use the `read_file` tool” or a request for a path the user already provided.

### Questions to investigate

1. How should we prompt the model to select the right tool and consistently produce the required tool-call format?
1. When a correctly formatted tool call includes additional natural-language text, should that text be shown to the user?

A smaller question is how best to present a successful tool result so the model produces a natural answer. My current candidate is the `grounded` instruction with raw JSON; it still needs further testing.
